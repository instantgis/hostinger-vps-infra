# Answers to vaultKISS Install Script Questions

## 1. Token exposure & logging

**Decision:** Use the simple one-liner. These are customer VPS installs, not CI pipelines. The token is single-use for initial setup - after install, the VPS fetches secrets via the token stored in a .env file. If a token leaks, it can be rotated in vaultKISS.

Document the simple pattern only:
```bash
curl -sf "https://vaultkiss.netlify.app/api/install?token=THEIR_TOKEN" | bash
```

Don't overcomplicate it.

## 2. Template name to filename mapping

**Decision:** Template names are already constrained. Current templates: `autolift-api`. Keep it simple:

- Use template `name` directly as filename
- Enforce slug-like names (lowercase, hyphens, no spaces) at template creation time
- No need for a separate `slug` column
- **One script per template** - no variants. The script should work on Ubuntu (the only supported VPS OS for now).

If we ever need variants, we'll add them later.

## 3. Where does the script live?

**Decision:** 

- **Short term:** Maintainer uploads `autolift-api.sh` via Supabase Dashboard > Storage
- **Long term:** Maybe a vaultKISS UI to edit/upload scripts, but not now
- **Show install snippet:** Yes, on the app detail page, show the curl command with the app's token

## 4. Token in query param vs Authorization header

**Decision:** Query param only for `/api/install`. Reason: `curl | bash` one-liner UX.

The `/api/secrets` endpoint uses Authorization header because it's called from within running containers (Docker entrypoint scripts) where headers are easy. The `/api/install` is a human typing a curl command - query param is simpler.

No need to support both. Keep it simple.

## 5. Responsibilities of install.sh

**Minimum contract for install.sh:**

1. Validate token works (call vaultKISS)
2. Check VPS is "clean" (not already installed)
3. Install Docker if needed
4. Create directory structure
5. Download docker-compose.yml and Caddyfile (embedded in script or from Docker image)
6. Fetch secrets, create .env files
7. Start containers
8. Health check

**Scripts are user-authored.** vaultKISS just serves them with token/secrets embedded. No generation.

**Ubuntu only** for now. No Alpine/other variants.

## 6. Safety, rate limiting, observability

**Rate limiting:** Not now. If a token leaks, rotate it. Netlify has some built-in protection.

**Logging install events:** Nice to have but not MVP. Add later if needed.

**Script size cap:** No. Trust the maintainer. The bucket is private anyway.

## 7. Placeholder semantics

**REVISED DESIGN - No placeholders needed!**

The `/api/install` endpoint should return a "fat" script:

1. Validate token
2. Fetch secrets for that app
3. Fetch script template from storage
4. Embed secrets directly as a heredoc or variables in the script
5. Return self-contained script

No `{{VAULTKISS_TOKEN}}` placeholder. No second call to `/api/secrets`. One curl, everything included.

Example output from `/api/install`:
```bash
#!/bin/bash
# AutoLift Installer - generated by vaultKISS

# Secrets (fetched at generation time)
POSTGRES_PASSWORD="actual_value_here"
SUPABASE_URL="actual_value_here"
# ... etc

# Rest of install script follows...
```

The script is fully self-contained. Customer runs it once, done.
